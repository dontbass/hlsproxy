# HLS Proxy (анти-фриз) для OpenWrt

Кэширующий HLS-прокси с отложенным эфиром. Работает на роутере (aarch64), принимает
плейлист провайдера (список каналов m3u, master или media m3u8) и отдаёт плееру
(OTT Navigator и т.п.) эфир с отставанием. За счёт этого отставания провалы скорости
и зависания провайдера гасятся.

```sh
wget -qO- https://raw.githubusercontent.com/dontbass/hlsproxy/main/install.sh | sh
```

Где найти: LuCI → Службы → HLS Proxy (генератор ссылки, настройки, состояние каналов).
Ссылка для плеера: `http://<роутер>:8888/playlist?url=<urlencoded ссылка провайдера>`.

## Как работает

- На каждый канал работает свой воркер. Он сам опрашивает плейлист провайдера и качает
  сегменты в `/tmp/hls_cache` (RAM) **по порядку**, по умолчанию в 2 потока.
- Плееру отдаётся плейлист, край которого отстаёт от эфира на `delay` секунд.
  Край двигается **строго по часам** и **только по полностью скачанным сегментам**.
  Плеер никогда не получает ссылку на сегмент, которого ещё нет.
- Загрузка без общего таймаута. Если 12 с не пришло ни байта, загрузка обрывается,
  затем **докачивается через Range**. Длина сверяется с Content-Length. HTML/JSON вместо
  видео отбрасывается. Битый или недокачанный сегмент в кэш не попадает.
- Если провал провайдера длиннее запаса, край ждёт, а после восстановления догоняет
  расписание пачкой (до `max-burst` сегментов) и возвращает плееру буфер.
- Если сегмент потерян (8 попыток), он пропускается с `#EXT-X-DISCONTINUITY`, поток не встаёт.
- Из master-плейлиста остаётся только лучшее качество: смена качества означает холодный
  старт и фриз.
- Канал без зрителей 60 с останавливается, кэш чистится.

## Панель и диагностика (v3)

`http://<роутер>:8888/ui` (также встроена в LuCI). По каждому каналу показывает:

- **Вердикт:** можно ли погасить провалы буфером:
  - ✓ *Запаса хватает*;
  - ! *Исправимо параметром delay*: нужная защита помещается в окно плейлиста провайдера;
  - ! *Исправимо, но только паузой*: окно провайдера короче нужного, недостающее набирается одной паузой;
  - × *Полностью не исправить*: провалы длиннее `max_delay`;
  - ! *На грани* или × *Провайдер медленнее потока*: средняя скорость ≈ битрейту или ниже, буфер даст только отсрочку;
  - плюс потери сегментов у провайдера: эти секунды эфира пропадут при любом буфере.
- **Шкала защиты:** текущая защита, сколько нужно (по худшему провалу за 10 мин), окно провайдера.
- **Рекомендация** `delay` / потоков с оценкой RAM и кнопкой «Применить для канала» (сохраняется в профиль).
- **Графики:** запас и потребность во времени (полосы: край ждёт / фриз у плеера / пауза-добор),
  опоздание каждого сегмента относительно линии защиты, скорость скачивания каждого сегмента в × реального времени.
- **События**, таблица сегментов, JSON: `/api/status`, `/api/channel/<id>`, `/api/profiles`.

### Журнал и разбор фризов (v3.1)

- **Кнопка «Был фриз»** (только что / 15 / 30 / 60 с назад) на панели. Прокси разбирает этот момент и называет причину:
  кончился запас, медленный Wi-Fi/LAN до ТВ, дефект в потоке провайдера, потерянный сегмент, обрыв или перезапуск у плеера.
  Если со стороны прокси всё чисто, так и пишет: причина в плеере или ТВ (декодер, автовыбор частоты кадров).
- **Анализ MPEG-TS каждого сегмента:** потерянные TS-пакеты (CC), дыры в кадрах (DTS), скачки времени на стыках, сегмент
  короче заявленного. Такие дефекты дают фриз при любом буфере, и при просмотре напрямую тоже.
- **Доставка роутер → ТВ:** для каждого сегмента время отдачи, скорость, обрывы со стороны плеера; паузы в опросе плейлиста.
- **Постоянный журнал** в `log_dir` (по умолчанию `/tmp/hlsproxy-log`, RAM):
  - `events.log` — все события всех каналов с датой, ротация 2 МБ (`/api/log?n=1000`);
  - `sessions/*.json` — снимок каждого сеанса (последний час сэмплов, сегменты, доставка, события, отметки);
    сохраняется каждые 5 мин, при отметке и при остановке канала, хранится 60 последних. Открываются в панели («История сеансов»).
  - Чтобы журнал переживал перезагрузку, укажите `log_dir` на USB/флеше.

### Как считается

- Для каждого сегмента известна позиция на шкале эфира и момент, когда он стал готов в RAM.
  **Опоздание** — насколько позже лучшего случая он готов.
- **Нужно** — максимальное опоздание за 10 мин. **Защита** — отставание края плейлиста плюс буфер плеера.
  Фриз происходит, если опоздание > защиты.
- **Ёмкость канала** — секунд контента, скачанных за секунду работы загрузчика. Если она < 1 при загрузчике,
  занятом почти всё время, буфер не поможет.
- Буфер плеера оценивается по модели ExoPlayer (старт с 2,5 с, после фриза с 5 с), фризы помечены как «оценка».

### Авто-режим (`mode auto`)

- **Профиль на канал** (`/etc/hlsproxy/profiles.json`): запоминается нужный `delay` и число потоков. Новый сеанс канала
  стартует сразу с нужным отставанием, если окно провайдера позволяет.
- **Потоки:** если загрузчик не успевает (ёмкость < 1,6 и очередь растёт), добавляется поток (до 4). При избытке скорости поток убирается.
- **Авто-пауза:** если плеер уже встал, а защиты не хватает, прокси не отдаёт ему сегмент сразу. Сегмент уходит по одному
  TS-пакету раз в 3 с: соединение живо, плейлист обновляется, ExoPlayer не считает поток зависшим. Через `max_pause`
  секунд или когда защита набрана, сегмент уходит целиком. Одна пауза чуть длиннее вместо серии фризов. Набранное время остаётся защитой до конца сеанса.

## Сохранённые плейлисты (v3.3)

LuCI → HLS Proxy → «Плейлисты»: название и ссылка провайдера хранятся на роутере (`config playlist 'pl_<id>'`
в `/etc/config/hlsproxy`). В плеер вставляется короткая ссылка:

- дома: `http://192.168.1.1:8888/pl/<id>`;
- извне: `http://<белый IP>:8888/k/<ключ>/pl/<id>`.

Когда провайдер меняет ссылку, достаточно поправить её на роутере: на ТВ ничего перебивать не нужно, и токен провайдера в ТВ не хранится.
После перевыпуска ключа внешние ссылки на странице пересчитываются сами. Прокси перечитывает список без перезапуска.

## Доступ извне (v3.2)

Для ТВ в другом месте, когда у роутера белый IP. Включается в LuCI → «Доступ извне».

- Клиенты из LAN и VPN (частные адреса, а также 100.64/10 — Tailscale) работают без ключа, как раньше.
- Внешние клиенты допускаются **только с ключом**: `http://<белый IP>:8888/k/<access_key>/playlist?url=...`.
  Ключ выпускается при установке (`uci get hlsproxy.main.access_key`), его можно перевыпустить в LuCI.
  Все ссылки, которые прокси отдаёт внешнему клиенту, уже содержат ключ. Панель тоже доступна: `/k/<ключ>/ui`.
- Внешний клиент не может заставить прокси сходить во внутреннюю сеть: частные адреса разрешены, только если
  этот хост уже встречался в плейлистах провайдера (например, IPTV провайдера на 10.x). `/ts` извне закрыт.
- Флаг «Открыть порт на WAN» создаёт правило файрвола `Allow-HLSProxy` (tcp/порт из wan). Без флага порт закрыт.
- Провайдер видит все запросы с твоего домашнего IP. Нагрузка ложится на исходящий канал дома: UHD 20 Мбит/с — это ≥ 25–30 Мбит/с отдачи на каждый внешний ТВ.
- **Защита:**
  - ключ — 122 бита случайности (UUID v4), сравнение за постоянное время;
  - IP, с которого пришло 20 неверных попыток за 10 мин, блокируется на час;
  - без ключа и с неверным ключом сканер получает обычный 404: прокси не выдаёт, что за порт;
  - соединение на белый адрес роутера считается внешним, даже если источник «частный»;
  - для запросов внешних клиентов каждый адрес проверяется при подключении, поэтому
    редирект или DNS-rebinding на внутренний адрес не пройдут;
  - по ключу извне доступен **только просмотр** (`/playlist`, `/proxy`, `/seg`), а панель и API работают только
    из LAN (`ext_ui 1` включает их для внешних клиентов);
  - внешний клиент не может заставить прокси подключиться к самому роутеру ни по одному его адресу,
    включая белый: к LuCI и SSH через прокси не достучаться;
  - внешние клиенты одновременно открывают не больше 2 каналов, всего каналов не больше 6 (защита RAM).
- Ключ передаётся открытым HTTP: его видит любой на пути (Wi-Fi у удалённого ТВ, провайдеры). С ключом можно
  смотреть IPTV через твой IP и менять параметры каналов в панели, но не попасть в LAN и не открыть LuCI.
- Без открытия порта: WireGuard между роутерами, и внешний ТВ ходит на `http://<IP в туннеле>:8888/playlist?url=...` без ключа.

## Настройки (`/etc/config/hlsproxy` или LuCI)

| опция | по умолч. | смысл |
|---|---|---|
| mode | auto | auto / advise / off |
| delay | 60 | отставание для канала без профиля, сек. Фактически не больше окна плейлиста провайдера |
| max_delay | 180 | потолок защиты для авто-режима, сек |
| max_pause | 40 | макс. одна авто-пауза, сек (0 — без пауз) |
| start_segs | 3 | сегментов на старте (собственный буфер плеера) |
| window | 8 | сегментов в плейлисте плеера |
| concurrency | 2 | параллельных загрузок на канал |
| all_variants | 0 | 1 = не выкидывать качества из master |
| ua | | User-Agent к провайдеру (пусто = как у плеера) |
| wan_access | 0 | 1 = открыть порт на WAN (правило файрвола) |
| access_key | (генерируется) | ключ для внешних клиентов, пусто = извне запрещено |
| log_dir | /tmp/hlsproxy-log | журнал и история сеансов |

## Диагностика

`http://<роутер>:8888/status` (то же самое в LuCI):

- `delay_s`: фактическое отставание от провайдера;
- `ready_ahead_s`: готовый запас в RAM впереди плеера;
- `realtime_x`: во сколько раз быстрее реального времени качаются сегменты (< 1.2 — плохо);
- `stalls`: сколько раз запас исчерпывался (провал был длиннее запаса).

Если на ТВ фризы, а `stalls = 0`, проблема не в доставке. Возможные причины: сам поток
провайдера, Wi-Fi до ТВ, декодер.

Логи: `logread -e hlsproxy -f`.

## Сборка

```sh
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o bin/hlsproxy_aarch64 .
SIM=1 SIM_WINDOW=15 SIM_DELAY=10 SIM_MAX_STALLS=0 go test -run TestSim -v   # симуляция нестабильного провайдера
SIM=1 SIM_RATE=90000 SIM_MODES=auto SIM_MAX_STALLS=99 go test -run TestSim -v  # провайдер медленнее потока
DEMO=1 go test -run TestDemo   # демо на :18888/ui
```
